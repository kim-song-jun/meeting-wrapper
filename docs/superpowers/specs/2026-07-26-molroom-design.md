# molroom — 사내 회의실 예약 시스템 설계

- 작성일: 2026-07-26
- 대상: molcube.com (Google Workspace)
- 상태: 설계 확정, 구현 전 스파이크 테스트 대기

---

## 1. 목적

molcube 구성원이 회의실을 **가장 적은 클릭으로** 잡고, 그 예약이 **각자의 Google 캘린더에 자동으로 나타나게** 한다.

핵심 제약은 사용자가 처음부터 제시한 것이다: **운영할 데이터베이스를 만들지 않는다.**

이 설계는 그 제약을 우회가 아니라 정공법으로 만족시킨다. molcube는 이미 Google Workspace를 쓰고 있고, Google Calendar에는 이미 회의실 예약을 위한 **리소스 캘린더**가 있다. 예약 데이터의 원본을 Google Calendar에 두면 저장소·중복방지·초대·알림·개인 캘린더 동기화를 전부 구글이 운영한다.

**molroom은 그 위에 얹는 더 빠른 UI다.**

---

## 2. 핵심 설계 결정

각 결정은 검토한 대안과 채택 이유를 함께 적는다. 나중에 이 문서를 읽는 사람이 "왜 이렇게 했지"를 되묻지 않도록.

### 2.1 예약의 원본은 Google Calendar다

| 대안 | 채택 여부 | 이유 |
|---|---|---|
| **Google Calendar가 원본** | ✅ 채택 | 저장소·초대·알림·개인캘린더 동기화를 구글이 처리. 우리 작업량 0 |
| 앱 자체 저장소(S3/KV)가 원본 | ❌ | 중복방지·알림·동기화를 전부 직접 구현해야 함. "간단한"과 멀어짐 |
| 하이브리드 양방향 동기화 | ❌ | 충돌 해결 로직이 가장 복잡. 이 규모에 과함 |

### 2.2 예약은 **사용자 본인 계정**으로 생성한다 (봇 계정 아님)

처음에는 서비스 계정(봇)에 회의실 캘린더를 공유해 예약을 대신 만드는 방식을 검토했다. 보안 사고 반경이 가장 작기 때문이다. **이 방식은 검증 결과 사용 불가로 판명됐다.**

리서치 결과 (2026-07-26, 공식 문서로 확정. 적대적 반박 검증에서도 기각되지 않음):

- 도메인 전체 위임(DWD) 없는 서비스 계정은 **참석자 초대를 보낼 수 없다**
  - Google 공식 레퍼런스가 `attendees[]` 필드 설명에 명시: *"Service accounts need to use domain-wide delegation of authority to populate the attendee list."*
    ([Events: insert 레퍼런스](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert))
  - 예외 조항이 없다. 회의실 캘린더에 ACL 쓰기 권한을 줘도 마찬가지
  - 실제 403 응답에 `forbiddenForServiceAccounts` 라는 전용 사유 코드가 붙는다 — 일반 권한 검사와 별개인 **호출자 신원 검사**임을 뜻한다
- 같은 조건에서 **Google Meet 링크 자동 생성도 사실상 불가**
  - 위임 없이 성공한 사례를 하나도 찾지 못함

초대와 Meet 링크는 이 제품의 핵심 요구사항이므로 봇 방식은 폐기했다.

**채택한 방식:**

```
[김철수 본인] ──생성──▶ 김철수의 캘린더 이벤트
                       ├ 참석자: 회의실(resource) + 동료들
                       ├ Meet 링크 자동 생성
                       └ 초대장·알림 자동 발송
                                 │
                       구글이 자동 복사
                                 ▼
                       회의실 캘린더  ← 조회 격자는 여기를 읽음
```

이는 사람이 Google 캘린더 UI에서 회의실을 잡는 것과 **완전히 동일한 동작**이다. molroom은 그 과정을 감싼 UI다.

이 방식의 이점:
- 주최자가 봇이 아니라 실제 예약자 (캘린더에서 자연스럽게 보임)
- 초대·알림·개인캘린더·Meet 전부 정상 작동
- 도메인 전체 위임 불필요 → 각 사용자는 자기 캘린더 권한만 부여. 사고 반경 최소
- 관리해야 할 서비스 계정 키가 존재하지 않음

### 2.3 서버와 데이터베이스를 두지 않는다

브라우저가 사용자 본인의 토큰을 들고 있으면 Google API를 직접 호출할 수 있다(구글 API는 CORS 지원).

**보안 경계는 이미 구글에 있다.** 외부인이 molroom URL을 열어도 자기 구글 계정으로는 molcube 회의실 캘린더에 접근 권한이 없어 아무것도 조회·예약할 수 없다. 우리가 별도로 지킬 자산이 없다.

앱이 필요로 하는 데이터 4종은 각자 집이 있다:

| 데이터 | 저장 위치 | 서버 필요 |
|---|---|---|
| 예약 전체 | Google Calendar | 없음 |
| QR 체크인 여부 | 이벤트의 `extendedProperties.shared` | 없음 |
| 내 기본 Zoom 링크 | Google Drive `appDataFolder` | 없음 |
| 회의실 목록·관리자 목록·예약 규칙 | 리포의 설정 파일 (빌드에 포함) | 없음 |

결과: **정적 HTML/CSS/JS 파일 + Google API.** 서버 코드 0줄, DB 0개, 시크릿 0개, 청구 계정 불필요.

**받아들인 트레이드오프:** 예약 규칙(최대 4시간 등)이 브라우저에서만 검사되므로 개발자도구로 우회 가능하다. 사내 도구라 우회 동기가 없고, 우회해도 구글이 권한을 강제하므로 남의 예약을 망가뜨릴 수는 없다. 규칙 강제가 실제로 필요해지면 v2에서 얇은 백엔드를 얹는다.

### 2.4 화상회의 링크: Meet 자동 + Zoom은 붙여넣기

Zoom API로 미팅을 자동 생성하는 방식은 검토 후 폐기했다: Pro 라이선스(월 $14~17), S2S OAuth 앱과 시크릿 관리, 생성/수정/삭제 합산 **하루 100건 제한**(연장 버튼이 한도를 소모), 예약 취소 시 Zoom 미팅 동기화 필요.

대신 **사용자가 자기 Zoom 링크를 붙여넣는다.** 유료 플랜·시크릿·호출 제한·동기화가 전부 사라지고, 화상링크는 이벤트에 넣는 텍스트 한 줄이 된다.

붙여넣은 링크는 **Google Drive `appDataFolder`에 사용자별로 저장**해 다음 예약 때 자동으로 채운다. localStorage가 아닌 클라우드에 두는 이유: QR로 폰에서 예약할 때 데스크톱의 localStorage는 보이지 않는다. QR 예약에서 링크를 손으로 타이핑하게 만들면 그 기능이 반쪽이 된다. localStorage는 오프라인 캐시로만 쓴다.

### 2.5 노쇼는 자동 취소하지 않고 표시만 한다

시작 후 일정 시간이 지나도 체크인이 없으면 격자에 "미체크인" 배지를 띄우고 예약은 유지한다.

이 결정의 부수 효과가 크다: **백그라운드 크론 잡이 통째로 불필요해진다.** "시작 10분 경과 + 체크인 기록 없음"은 화면을 그릴 때 계산하면 되므로 서버에서 돌 것이 없다. 2.3의 인프라 제로가 성립하는 조건 중 하나다.

또한 체크인을 깜빡한 진짜 회의가 자동 삭제되는 사고 위험이 0이다.

### 2.6 그 외 확정 사항

| 항목 | 결정 |
|---|---|
| 조회 격자 상세도 | **주최자 이름까지** 표시, 회의 제목은 숨김 (프라이버시) |
| 예약 수정·취소 권한 | **본인 + 관리자.** 관리자 목록은 설정 파일 |
| 예약 규칙 | 느슨하게 — 최대 4시간, 4주 전까지, 횟수 무제한. 전부 설정 파일 값 |
| 프론트엔드 스택 | Vite + React + TypeScript |
| 회의실 목록 | 설정 파일에 하드코딩 (Directory API는 관리자 권한이 필요해 일반 사용자 토큰으로 못 부름) |

## 3. 아키텍처

```
┌──────────────────────────────────────────────────┐
│  정적 파일 (Vite 빌드 결과)                        │
│  rooms.molcube.com                               │
│  - 예약 격자 / 예약 모달 / QR 랜딩 / 내 예약·설정   │
└────────────────────┬─────────────────────────────┘
                     │ 사용자 본인의 OAuth 액세스 토큰
         ┌───────────┼────────────┐
         ▼           ▼            ▼
   Calendar     Calendar      Drive
   읽기          쓰기          개인설정
   ─────────    ─────────     ─────────
   freebusy     events.insert  appDataFolder
   events.list  events.patch   (기본 Zoom 링크)
                events.delete
```

호스팅은 정적 파일을 서빙할 수 있으면 어디든 무방하다 (S3+CloudFront, Firebase Hosting, GitHub Pages, Cloudflare Pages). 이 선택은 설계에 영향을 주지 않으므로 배포 시점에 정한다.

### 3.1 인증

- Google Identity Services (GIS) **authorization code + PKCE** 흐름이 아닌, 정적 SPA이므로 **토큰 클라이언트(`initTokenClient`)** 사용
- 요청 스코프:
  - `calendar.events` — 예약 생성·수정·삭제
  - `calendar.readonly` — 회의실 캘린더 조회
  - `drive.appdata` — 개인 설정 저장
- `hd: molcube.com` 파라미터를 붙이되, **이것은 계정 선택 UI를 좁히는 UX 힌트일 뿐 보안 장치가 아니다.** 실제 접근 통제는 구글의 캘린더 권한이 한다 (2.3 참조)
- OAuth 동의 화면은 **Internal(조직 내부용)** 로 설정 → 구글 앱 심사 면제

### 3.2 세션 정책 — 사용자는 사실상 다시 로그인하지 않는다

Google OAuth 액세스 토큰의 수명은 **1시간이며 애플리케이션이 바꿀 수 없다.** 구글이 고정한 값이다.

하지만 그것이 "1시간마다 로그인해야 한다"를 뜻하지는 않는다. 실제 동작은 이렇다:

| 계층 | 수명 | 누가 정하나 |
|---|---|---|
| 액세스 토큰 | 1시간 | 구글 (변경 불가) |
| molroom 앱 세션 | 토큰이 조용히 갱신되는 한 계속 | 우리 |
| 구글 로그인 세션 | 기본 무기한 | **Workspace 관리자의 세션 제어 설정** |

동작:
1. 토큰 만료가 가까워지면 GIS 토큰 클라이언트로 **무음 재발급**을 요청한다 (동의 프롬프트를 요구하지 않는 모드)
2. 사용자가 이미 동의했고 구글 세션이 살아 있으면 화면에 아무것도 뜨지 않고 새 토큰을 받는다
3. 무음 재발급이 실패했을 때만 "다시 연결" 배너를 띄운다. 조용히 실패하지 않는다

따라서 "사내용이니 24시간 정도 유지" 요구는 충족되며, 실제로는 관리자가 세션 제어를 따로 조이지 않는 한 그보다 길다.

**미검증:** 브라우저의 서드파티 쿠키 정책 강화가 무음 재발급을 방해할 수 있다. 10장 스파이크 테스트 8번에서 확인한다. 실패하면 인증 코드 교환을 위한 얇은 백엔드가 필요해지고, 인프라 제로가 깨진다.

## 4. 데이터 모델

예약 하나 = Google Calendar 이벤트 하나. 별도 스키마가 없다.

| molroom 개념 | Calendar 이벤트 필드 |
|---|---|
| 회의 제목 | `summary` |
| 시작 / 종료 | `start.dateTime` / `end.dateTime` |
| **회의실** | `attendees[]` 중 `resource: true` 인 항목 |
| 주최자 | `organizer` (= 예약자 본인) |
| 참석자 | `attendees[]` |
| Google Meet 링크 | `conferenceData` |
| Zoom 링크 | `location` |
| 알림 | `reminders` |
| molroom이 만든 예약 표식 | `extendedProperties.shared.molroom` |
| QR 체크인 시각 | `extendedProperties.shared.checkedInAt` |

`extendedProperties.shared`를 쓰는 이유: `private`은 이벤트를 만든 사람에게만 보이므로, 다른 사람이 격자에서 "미체크인" 배지를 볼 수 없다. **단 회의실 캘린더 사본에서 `shared`가 실제로 읽히는지는 미검증이며, 5.1의 첫 스파이크 테스트 대상이다.**

### 4.1 설정 파일

```jsonc
// src/config/rooms.json
[
  {
    "id": "room-a",
    "email": "molcube.com_xxxxx@resource.calendar.google.com",
    "name": "3층 회의실 A",
    "capacity": 8,
    "floor": "3F"
  }
]
```

```jsonc
// src/config/policy.json
{
  "maxDurationMinutes": 240,
  "maxAdvanceDays": 28,
  "gridStartHour": 8,
  "gridEndHour": 20,
  "slotMinutes": 30,
  "checkInGraceMinutes": 10,
  "extendStepMinutes": 15,
  "admins": ["someone@molcube.com"]
}
```

## 5. 화면 명세

**모바일과 데스크톱 모두 1급으로 지원한다.** 데스크톱 전용 앱에 모바일을 끼워 넣는 것이 아니라, 두 형태에서 각각 다른 일을 하기 때문이다:

| | 주 사용 맥락 | 핵심 동작 |
|---|---|---|
| 데스크톱 | 자리에서 미리 잡기 | 격자를 훑고 시간대 비교 후 예약 |
| 모바일 | 복도에서 QR 찍고 즉시 | 지금 비었는지 보고 2탭에 예약 / 체크인 / 연장 |

격자 화면도 모바일에서 동작해야 하지만(하루 단위 세로 스크롤로 축약), 모바일의 주 진입점은 QR 랜딩이다.

디자인 토큰·컴포넌트는 프로젝트 루트의 `DESIGN.md`를 따른다.

### 5.1 예약 격자 (데스크톱 주력, `/`)

세로축 = 시간(설정의 `gridStartHour`~`gridEndHour`, `slotMinutes` 단위), 가로축 = 회의실.

```
        3층 A(8)   3층 소(4)   4층 B(12)
 09:00 │         │           │
 09:30 │ 김철수   │           │ ▓▓▓▓▓▓▓
 10:00 │ ~10:30  │           │ 이영희
 10:30 │         │  ░░░░░░   │ ~11:00
 11:00 │         │  내 예약   │
```

- 찬 칸: 주최자 이름 + 종료 시각. 회의 제목은 표시하지 않음
- 내 예약: 별도 색으로 강조
- 미체크인(시작 후 `checkInGraceMinutes` 경과, 체크인 기록 없음): 배지 표시
- 빈 칸 드래그 → 시간 범위 선택 → 예약 모달
- 날짜 이동 (오늘 / 내일 / 날짜 선택)

### 5.2 예약 모달

- 회의실 (격자에서 선택된 값, 변경 가능 — 정원 함께 표시)
- 시작·종료 시각 (프리셋 30분 / 1시간 / 직접 입력)
- 제목
- 참석자 (이메일 직접 입력)
- 화상회의: `없음` / `Google Meet 자동 생성`(기본값) / `Zoom` + 링크 입력
  - Zoom 선택 시 저장된 기본 링크를 자동으로 채움
  - "내 기본 링크로 저장" 체크박스
- 규칙 위반 시(4시간 초과, 4주 초과) 저장 버튼 비활성 + 이유 표시

### 5.3 QR 랜딩 (모바일, `/r/:roomId`)

회의실 문에 붙인 QR이 이 URL을 가리킨다. QR에는 **서명 토큰이 아니라 평범한 고정 URL**을 넣는다 — QR은 사진 찍어 공유하면 그만이라 토큰을 넣어도 실질적 방어가 되지 않고, 실제 보안 경계는 구글 로그인이기 때문이다.

```
      3층 회의실 A · 8인
      ┌──────────────────┐
      │  🟢 지금 비어있음  │
      │  다음 예약 14:00  │
      └──────────────────┘
      [   30분 예약   ]
      [   1시간 예약   ]
      [ 14:00까지 전부 ]
```

- 사용 중이면: 주최자 + 종료 시각 표시, 다음 빈 시간대 안내
- **내 회의가 진행 중이면**: `[체크인] [+15분 연장] [지금 종료]`
- 첫 방문 시 구글 로그인 1회, 이후 자동

### 5.4 내 예약 / 설정 (`/me`)

- 내가 잡은 앞으로의 예약 목록 (수정·취소)
- 관리자인 경우: 전체 예약 조회·취소 탭
- 기본 Zoom 링크 설정

## 6. 핵심 흐름

### 6.1 예약 생성 — 중복 방지 3중 방어

Google Calendar는 트랜잭션 데이터베이스가 아니다. 이미 찬 회의실에 예약을 넣어도 `events.insert`는 **200 OK를 반환하고 이벤트를 만든 뒤**, 회의실이 비동기로 "거절"로 응답한다. 원자적 잠금이 아니라 사후 통보다.

따라서 세 겹으로 막는다:

```
[1] 화면 진입
      │  freebusy.query (전체 회의실 · 오늘~2주)
      ▼
[2] 격자 렌더 — 찬 칸은 클릭 불가          ◀── 1차 방어: 대부분 여기서 걸림
      │  사용자가 빈 칸 선택 → [예약] 클릭
      ▼
[3] 예약 직전 재조회 (그 방 · 그 시간만)   ◀── 2차 방어: 오래된 화면 방지
      │
      ├─ 이미 찼음 → "방금 다른 분이 예약했어요" + 격자 갱신 → 중단
      │
      ▼ 아직 비었음
[4] events.insert
      │   - attendees[]에 회의실을 resource: true 로 추가
      │   - conferenceData.createRequest (Meet 선택 시)
      │   - extendedProperties.shared.molroom 표식
      │   - sendUpdates: 참석자가 있으면 all, 없으면 none
      ▼
[5] 회의실의 responseStatus 재확인          ◀── 3차 방어: 구글의 사후 거절 감지
      │
      ├─ declined → 만든 이벤트 삭제(롤백) + "예약 실패" 안내
      │
      ▼ accepted
[6] 완료 — 초대장·알림·Meet 링크는 구글이 처리
```

**3차 방어가 가장 중요하다.** 이걸 빼면 사용자는 예약된 줄 알고 회의실에 갔다가 다른 팀이 쓰고 있는 상황을 겪는다.

### 6.2 연장 / 단축

- `+15분` / `-15분` 버튼 (`extendStepMinutes`)
- **누르기 직전에 회의실 캘린더를 다시 읽어** 다음 예약과 겹치는지 확인한다. 클라이언트 캐시로 판단하면 조용히 이중 예약이 된다
- 겹치면 버튼 비활성 + 이유 표시: `"14:00에 이영희님 예약 있음"`
- `events.patch`로 `end.dateTime`만 수정
- `sendUpdates`: 참석자가 나 혼자면 `none` (혼자 쓰는 회의를 연장할 때마다 메일이 가면 스팸이 된다). 다른 참석자가 있으면 `all`

### 6.3 QR 체크인

- QR 스캔 → `/r/:roomId` → 로그인 → 진행 중인 내 회의가 있으면 `[체크인]` 버튼
- `events.patch`로 `extendedProperties.shared.checkedInAt`에 현재 시각 기록
- 격자에서 "시작 후 `checkInGraceMinutes` 경과 + `checkedInAt` 없음" → 미체크인 배지
- **자동 취소는 하지 않는다** (2.5)

## 7. 권한과 보안

| 관심사 | 처리 주체 |
|---|---|
| 외부인 접근 차단 | **구글.** 회의실 캘린더에 권한이 없으면 조회·예약 불가 |
| 남의 예약 수정 차단 | **구글.** 남의 캘린더 이벤트는 애초에 못 건드림 |
| 관리자의 전체 예약 취소 | 관리자를 회의실 캘린더의 writer로 지정 → 회의실 캘린더의 사본을 제거해 방을 비움. 앱은 설정 파일의 `admins`로 UI만 노출 |
| 예약 규칙(4시간 등) | **브라우저에서만 검사.** 우회 가능하나 사내 도구이고 우회해도 남에게 피해가 없음 (2.3의 트레이드오프) |
| 시크릿 관리 | 해당 없음 — 저장하는 시크릿이 존재하지 않음 |

**주의:** `hd=molcube.com`은 보안 장치가 아니다. 계정 선택 화면을 좁히는 UX 힌트일 뿐이며, 실제 통제는 구글의 캘린더 접근 권한이 한다.

## 8. 에러 처리

| 상황 | 처리 |
|---|---|
| 액세스 토큰 1시간 만료 | 조용히 재발급 시도 → 실패 시 재로그인 배너 |
| 예약 직전 충돌 (2차 방어) | "방금 다른 분이 예약했어요" + 격자 즉시 갱신 |
| 회의실이 거절 (3차 방어) | 만든 이벤트 삭제 후 실패 안내 |
| 연장이 다음 예약과 충돌 | 버튼 비활성 + 사유 표시 |
| 오프라인 | 조회는 마지막 캐시 표시(오래됨 배지), 쓰기 차단 |
| Calendar API 쿼터 초과 | 지수 백오프 재시도 → 실패 시 안내 |
| 회의실 목록 설정 오류 | 부팅 시 회의실 캘린더 접근을 검사해 문제 있는 항목을 경고 |

빈 `catch`는 두지 않는다. 모든 실패는 사용자에게 보이거나 콘솔에 남는다.

### 9.1 Mac 앱을 만들지 않는 이유

검토 결과 v1에서는 불필요하다. 설치형 PWA로 독 아이콘, 자체 창, QR 스캔용 카메라 접근, 알림까지 전부 커버된다 (macOS Safari 16+는 웹 푸시를 지원하며 Apple 개발자 프로그램이 필요 없다).

유일한 진짜 공백은 **메뉴바에서 다음 회의를 흘끗 보는 위젯**이다. 이건 어떤 웹 API로도 불가능하다. 실제로 필요해지면 Tauri v2로 기존 웹앱을 감싸는 것이 가장 싸다(며칠 작업, 5~10MB). 단 Gatekeeper 때문에 **Apple 개발자 프로그램 연 $99**가 필요하다. Electron은 같은 서명 요구에 번들만 10~20배라 이 용도로는 정당화되지 않는다.

## 10. 구현 전 스파이크 테스트

리서치로 확정하지 못한 항목이다. **코드를 쓰기 전에 실제 molcube 도메인에서 확인한다.** 예상 소요 30분~1시간.

| # | 확인할 것 | 실패 시 영향 |
|---|---|---|
| 1 | `extendedProperties.shared`가 **회의실 캘린더 사본에서도 읽히는가** | **치명.** 체크인 상태를 담을 곳이 없어짐 → 인프라 제로가 깨지고 Firestore 도입 필요 |
| 2 | 일반 사용자가 회의실 캘린더를 `events.list`로 **주최자 이름까지** 읽을 수 있는가 | 격자가 "차있음/비었음"만 표시하게 축소 |
| 3 | 사용자 토큰으로 Meet 링크 생성이 되는가 | Meet 기능 제거 또는 대안 필요 |
| 4 | 회의실 auto-accept/decline이 실제로 어떻게 동작하는가 (관리자 설정이 자동수락 ON인지 포함) | 3중 방어의 3차가 무의미해짐 → 방어 재설계 |
| 5 | Drive `appDataFolder` 읽기·쓰기 | 기본 Zoom 링크를 localStorage로 후퇴 (QR 예약에서 자동완성 불가) |
| 6 | 관리자가 남의 예약을 회의실 캘린더에서 제거 가능한가 | 관리자 권한 기능 재설계 |
| 7 | molcube의 Workspace 등급 확인 | 등급별 기능 제약 파악 (Room Insights 등은 Enterprise 전용) |
| 8 | **무음 토큰 재발급**이 실제 브라우저(Chrome/Safari, 데스크톱+모바일)에서 동작하는가 | **치명.** 1시간마다 재로그인하게 되어 사용성 붕괴 → 인증 코드 교환용 얇은 백엔드 필요, 인프라 제로 깨짐 |

1번과 8번이 가장 위험하므로 첫 작업으로 잡는다. 둘 다 실패 시 인프라 제로가 깨지며, 그 경우 Firebase 도입 여부를 사용자에게 확인받고 진행한다.

### 10.1 관리자 사전 작업

Workspace 관리자 콘솔에서 필요한 일회성 작업:

1. 각 회의실을 **캘린더 리소스**로 등록 (이름, 정원, 층)
2. 회의실 캘린더가 도메인 사용자에게 조회 가능하도록 공유 설정 확인
3. 회의실의 **초대 자동 수락**이 켜져 있는지 확인 (꺼져 있으면 중복 방지가 동작하지 않음)
4. Google Cloud 프로젝트 생성 + OAuth 클라이언트를 **Internal**로 설정
5. 관리자로 지정할 사람을 회의실 캘린더의 writer로 추가

## 11. 테스트 전략

검증은 변경의 위험에 비례해서 붙인다. 구글 API를 mock으로 감싸 "우리 코드가 우리가 짠 mock을 호출한다"를 확인하는 테스트는 쓰지 않는다 — 그런 테스트는 깨져도 실제 버그를 잡지 못한다.

**단위 테스트를 쓰는 곳** (실제 계약이 있고 틀리면 사고가 나는 순수 로직):
- 시간 구간 겹침 판정 (연장 가능 여부, 슬롯 충돌)
- freebusy 응답 → 격자 셀 변환
- 예약 규칙 검증 (최대 시간, 최대 선행일)
- 미체크인 판정 (시작 시각 + 유예 + 체크인 기록)

**단위 테스트를 쓰지 않는 곳:**
- Google API 호출 래퍼 (스파이크 테스트와 실제 사용으로 검증)
- 단순 렌더 컴포넌트

**실기기 검증** (UI 변경은 여기까지가 한 작업):
- 데스크톱 격자: 실제 브라우저 스크린샷으로 정렬·균형 확인
- QR 랜딩: 실제 폰 화면 폭에서 확인
- 3중 방어: 두 브라우저로 동시 예약을 시도해 2차·3차 방어가 실제로 걸리는지 확인
